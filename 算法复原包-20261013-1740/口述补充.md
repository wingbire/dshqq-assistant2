## 一、原始口述（逐字照录，未改写）

> 核心是本地的一套算法：通过语义分割、之前接收到的消息之间的联系、收到消息的连续性、人称代词的指代对象、其它群成员昵称和群头衔对应消息历史来构建一套评分体系。来判断每条消息是对小助手说的还是对其它群成员说的，然后通过这套评分系统综合设定一个阀门和灰区，通过直接调用api来进行二次复核。如果判定是否，就直接不回复，不经过大脑。如果判定为是，就直接进入大脑，给出回复；如果落在灰区，就由api调用其它模型经过外审判定是否经过大脑。同时设立另一个参数用相似的方式评估回复深度，决定经过大脑时是否进行联网搜索和搜索几次，以及决定搜索的关键词。最后再把本地，api复核和大脑不同程度调用的成本参数引入综合算法。同时再结合小助手主动发言或回复后是否有人愿意跟她接话，制作一个动态的自学习调参机制，达到逐渐契合群友兴趣和聊天习惯的方式。标注系统则是由管理的用户手动判定某个消息该不该回来校准本地算法和api调用复核的准确度。

## 二、结构化拆解（口述 → 组件）

### 2.1 第一层：本地评分体系（判断"这条消息是不是对我说"）

口述给出的**五个特征族**：

| # | 口述特征 | 对应实现（推断） | 证据情况 |
|---|---|---|---|
| 1 | 语义分割 | `classify.js`（话题/类型桶） | 仅片段 |
| 2 | 之前接收到的消息之间的联系 | `addressee.js` 的每群 IDF 语料 + `utility` 的 `v_sem` | **已取回**（addressee 306 行） |
| 3 | 收到消息的连续性 | `utility` 的 `v_cont`（被直接回复/刚说完/群里在聊我/全新话题） | **已取回**（utility 225 行） |
| 4 | 人称代词的指代对象 | 指代消解（她/他/它）+ 第二人称「你」判定 | ⚠️ 见 §三 对照 2 |

**【对照】** 与取回的 `utility.js` 六因子里的第 ① 项 `p_say（addressee 置信度）` **一致**。

### 2.2 阀门 + 灰区 + API 二次复核（三态判决）

口述的三态：

| 判定 | 动作 |
|---|---|
| 否 | **直接不回复，不经过大脑**（不调用 LLM） |
| 是 | **直接进入大脑**，给出回复 |
| 灰区 | **由 API 调用其它模型做外审**，决定是否经过大脑 |

**【对照】** 10/8《优化意见-v3-待评审》原文印证了灰区机制："assist 模式的**灰区复核**（`conf<0.75` 先问一次模型、模型说 IGNORE 就静音）与 `softForkBlocked` **已经在 fork 之前生效**"。
→ 证据给出的是**单边界 0.75**；口述描述的是**阀门 + 灰区（区间）**。需确认两个边界（见 §四 问题 2）。

### 2.3 第二层：回复深度参数（同名机制，独立评估）

口述：**"设立另一个参数用相似的方式评估回复深度，决定经过大脑时是否进行联网搜索和搜索几次，以及决定搜索的关键词。"**

→ 这是**证据里没有的一层**：恢复物中只有 `utility` 的 `d_diff`（回复难度，含"是否要长内容"）与三档深度（极短/常规/多讲两句），**没有"是否联网搜索 / 搜几次 / 关键词"的决策层**。
【对照】项目确实有搜索接入的痕迹（配置里存在 `llm.search.apiKey` 这类密钥位、本地装了 `dsh-free-search` 插件），但**该决策参数本身未取回**。

### 2.4 成本模型（三级）

口述：**"最后再把本地、api 复核和大脑不同程度调用的成本参数引入综合算法。"**

→ 即成本不是单一 token 项，而是**三级成本**：
1. **本地判定**成本（本地算力/时间）
2. **API 复核**成本（灰区外审的调用）
3. **大脑调用深度**成本（进 LLM 的 token / 搜索次数）

**【对照】** 取回的 `utility.js` 里成本是 `λ_eff · d_diff · (d_cost/costScale)`，`d_cost = 未命中输入 + 2×输出`（**计费 token 口径**）；`score.js` 里 `reward = engagement − λ·norm`。这对应的是**第 3 级的 token 部分**；第 1、2 级成本在恢复物里没有体现 → 需补口径（见 §四 问题 4）。

### 2.5 自学习调参

口述：**"结合小助手主动发言或回复后是否有人愿意跟她接话"** → 动态自学习，逐渐契合群友兴趣与聊天习惯。

**【对照】完全吻合**：
- `score.js`：`reward = engagement − λ·norm`，engagement 就是"有没有人接话"的量化
- 取回的 engagement 档位：`+4 接着聊并叫外号 / +2 接着说 / −1 没人接 / −2 嫌烦`
- `learner.js`（358 行，已取回）、`bandit.js`（188 行，已取回，Thompson Sampling 选话风臂）、`profile.js` 的 `PARAM_BOUNDS`（按群参数边界，未取回）

### 2.6 标注系统（人工校准）

口述：**"由管理的用户手动判定某个消息该不该回，来校准本地算法和 API 调用复核的准确度。"**

→ 这正好**填上了零证据的 `labels.js`**：它是**人工标注**（管理员判定该不该回），用途是**双目标校准**：
- 校准**本地算法**（权重/特征）

**【对照】** 10/8 文档提到的 N0 优先级是"① 线上人工标签 ② 本机沙箱可跑的全量测试入口 ③ 固定判定回归台"，与本条一致；但 `labels.js` 本身零证据 → 数据结构仍是空白（见 §四 问题 6）。

# 第二批口述（2026-10-13 18:42）

## 原始口述（逐字照录）

> 1.指代消解：目的是为了在不@的情况下（@就直接回复了）判断叫小助手外号和昵称，以及句子中出现多个人称代词的情况下，句意究竟是陈述性表达，还是指向性表达。2.灰区在fork前生效应该是综合判断决定回复深度，然后适当加权重判断三个档位的回复字数限制，如果深度参数不高，就不进大脑，直接短句回应，深度中就不搜索或只搜索一次总结回答；如果深度高就搜索一次，外审一次，详细回答。灰区边界是自适应调节的；成本核算就是根据单次确定的回复所花费的token；外审是使用的其它模型，返回应该为是/否/不确定；有人接话的判定是小助手输出对某个人回复一次后，那个人是继续跟小助手接着聊还是去跟别人聊。学习调整范围是每积累20次回复，将历史消息发给大脑提炼一次群档案，同时动态调整群聊专属关键词。

## 逐条拆解

### 1. 指代消解的真实目的（不是"消解第三人称实体"）

- **触发条件**：只在**不 @** 的情况下才需要（@ 就直接回复，不走这套）
- **要解决两类问题**：
  1. **外号与昵称的指向性** —— "叫小助手的那个外号/昵称"到底是不是在叫它
  2. **多个人称代词同现时的句意判别** —— 是**陈述性表达**还是**指向性表达**

**【对照 · 调和了上一轮的矛盾】** 10/8 文档建议"指代消解 MVP 降级并**改写方向**"，理由正是"实体表解决第三人称、帮不上第二人称"。口述给出的这两类问题（外号/昵称指向、陈述 vs 指向）**正是"改写方向"之后的形态** —— 它不再做实体表式的第三人称消解，而是做**指向性判别**。两说法可以并存：**审计提的方向修正，被采纳了。**

### 2. 灰区 ≠ "要不要回"，而是"回复深度分档"（fork 前生效的真实含义）

| 深度档 | 动作 |
|---|---|
| 深度**不高** | **不进大脑**，直接短句回应 |
| 深度**中** | 不搜索或**只搜一次**，总结回答 |
| 深度**高** | 搜索一次 + **外审一次** + 详细回答 |

- **灰区边界是自适应调节的**
- 用**适当加权**决定**三个档位的回复字数限制**

**【对照】** 这正好解释了 10/8 文档那句"灰区复核……**已经在 fork 之前生效**"——它生效的位置就是**决定要不要进大脑之前**。
→ 修正我此前的理解：**"说不说"由评分 + 阀门决定；灰区/深度分档决定的是"进不进大脑、搜不搜、说多少"**。

### 3. 成本核算口径

**"根据单次确定的回复所花费的 token。"**
**【对照】** 与取回的 `utility.js` 完全合上：`d_cost = 未命中输入 + 2×输出`（与计费口径一致）。
**【自我修正】** 我在上一轮把口述里"本地/api复核/大脑"读成"三级独立成本"——**读重了**。实际是：**一次确定的回复的总 token 成本**（其中天然包含复核与大脑的消耗）。

### 4. 外审

使用**其它模型**（不是同模型换 prompt），返回 **是 / 否 / 不确定**（三值）。

### 5. "有人接话"的精确定义

小助手**对某个人**回复一次后，看**那个人**是：
- **继续跟小助手接着聊** → 正反馈
- **转去跟别人聊** → 负反馈

**【对照】** 完美对上取回的 engagement 档位：`+4 接着聊并叫外号 / +2 接着说 / −1 没人接 / −2 嫌烦`。**这是"按被回复人"计的，不是按群平均计的。**

### 6. 学习节奏与范围

- **每积累 20 次回复** → 把**历史消息发给大脑提炼一次"群档案"**
- 同时**动态调整群聊专属关键词**

**【对照 · 三处强印证】**
1. `refN: 20`（`score.js` 的默认参数）**就是"每 20 次回复"这个基准** ✅
2. "群档案" ↔ `profile.js` + `模块.json` 里的 group-profile 模块 ✅
3. "动态调整群聊专属关键词" ↔ `TOPIC_DEPTH_K = 0.10` 所依赖的**话题词表**——原来它是**动态生成**的，不是人工固定 ✅

→ 处置不是固定的三态动作，而是**与本地判定联合决定**：
- 本地判**否** + 外审**不确定** → 调节**向下**（更浅，偏向不进大脑/短句）
- 本地判**不确定**（灰区） + 外审**不确定** → 按深度评分再定档
> 精确的联合规则表待补，但**判定输入**已明确：本地三态 × 外审三态。

### 4. 群专属关键词

**"每群一份，群友性格和兴趣和雷点之类的。"**
→ 每群一份；内容不是单纯关键词表，而是**群友性格 / 兴趣 / 雷点（禁忌）**这类画像要素。
→ 这同时回答了"动态调整"调的是什么：**调的是这份按群画像**。

### 5. 群档案的输出结构 = **大脑生成前的提示词（prompt 前缀）**

**"对每个群单独生效的，经过大脑输出内容前的提示词 promote。"**
→ 群档案**不是数据库 schema，而是一段每群单独的提示词**，在进大脑生成前注入。
→ 与 `profile.js` + group-profile 模块对应；`refN=20` 时由大脑重新提炼这份提示词。

## 第三批带来的新增确认

| 项 | 值/形态 |
|---|---|
| 三档字数 | **20 / 60 / 200+** |
| 全局人设提示词 | 决定精炼 vs 详细；并决定超限时"拆两条 vs 压缩成一条" |
| 自适应对象 | **灰区上下限** |
| 外审"不确定" | 与本地三态联合 → 调节回复深度 |
| 群档案 | **每群一段 prompt**（含性格/兴趣/雷点），大脑生成前注入，每 20 次回复重炼 |
